# Verification record: 0.4.1 (timeouts kill the whole process tree)

What was run, for real, before 0.4.1 was proposed for release. 0.4.1 is a
patch release with two fixes, both found by the integration suite added
after 0.4.0 ([INTEGRATION_TESTS.md](../INTEGRATION_TESTS.md)):

1. **Timeouts kill the whole process tree.** A timed-out dispatch killed
   only its direct child. On the `command` harness this left a wrapper's
   real agent running (seen: three orphaned stand-in agents). On Claude
   Code the same pattern would leave a `tend`'s builds and test runs running
   (gardener#187). Both harnesses now run the agent in its own session
   through `_run_in_process_group`, and kill the group on a timeout.
2. **A tampered report run says why it failed.** When a `command`-harness
   report run changed the clone, the run was failed, but the reason never
   reached the operator, and the run recorded the agent's own success
   summary. It is now `DispatchResult.failure_reason`, printed by `align`
   and recorded as the run's summary.

- **Code verified:** branch `fix/claude-timeout-process-group`. Fix 2 and
  the `command`-harness half of fix 1 merged in #188; see
  [orket-0.8.2.md](orket-0.8.2.md) for those runs.
- **Date:** 2026-10-11.
- **Environment:** WSL2 (Linux 5.10), Python 3.11.15 and 3.10.20, Claude
  Code CLI as installed.
- **Isolation:** every run used the integration suite's sandbox: its own
  state and cache, ambient settings removed, usage reporting off, no hub.

## Automated tests

- **Unit suite:** 1,112 tests OK, run with a booby-trapped `claude` first
  on `PATH`. The trap logged every invocation and logged none, so no unit
  test reaches a real `claude` through the new call.
- **Retargeted mocks:** the 17 `test_dispatch.py` tests that mocked
  `subprocess.run` for `claude` now mock `_run_in_process_group`, the one
  call `claude` goes through.
- **New unit test:** `TestClaudeTimeoutKillsProcessTree` uses a fake
  `claude` script that starts a child and sleeps. After a 3 s timeout, the
  child must be gone.
- **Offline integration test:** `test_timeout_kills_claudes_children` does
  the same through the real `gardener align` CLI.
- **Both tests fail with the fix reverted** ("claude's child outlived the
  timeout"). The `command`-harness equivalents were checked the same way
  in #188.
- **Offline integration tier:** OK.

## Real Claude Code runs

| Run | Code | Result |
|---|---|---|
| Report `align`, fixture target, no timeout | this branch | exit 0 in 25 s, $0.14, "6 gap(s) found across 4 section(s)", clone unchanged |
| Report `align`, `GARDENER_ALIGN_TIMEOUT=20` | this branch | timed out at 20.2 s, exit 1, clone unchanged, no process left in the sandbox |
| The same, timeout 20 s | `main` before the fix | the same result |

The first row is the regression check that matters. `claude` now starts in
its own session, and a complete real dispatch still works from there.

The timed-out runs show no difference before and after. That is expected:
report mode gives `claude` no shell, so it starts no lasting children to
leave behind. The case the fix is for, a `tend` whose build outlives the
timeout, was not reproduced with a real `claude`: it needs a real write-mode
dispatch timing out mid-build. It is covered by the fake-`claude` tests
above, which fail without the fix.

## Not changed

- `gardener stop`/`kill` already signal the whole `/proc`-walked tree. A
  child in its own session is still a descendant, so they are unaffected.
- If gardener itself is killed by a signal it does not handle (for example
  `SIGTERM` to the gardener process alone), the agent's group is not
  killed. That was also true before: such a signal never reached the
  children. `KeyboardInterrupt` and other exceptions inside the call do
  kill the group.
