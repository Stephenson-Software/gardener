# Verification record: 0.4.4 (overnight continues into the next cycle)

What was run before 0.4.4 was proposed for release.

- **Code verified:** branch `fix/overnight-continue-next-cycle`.
- **Date:** 2026-10-11.
- **Environment:** WSL2 (Linux 5.10), Python 3.11.15 and 3.10.20, git
  2.25.1.

## The bug

Under `--strategy random` or `issue-count`, `overnight` works through the
garden once per cycle and records the repos it has attempted. A run that
started with only a few repos left in the cycle tended those and stopped.
The next cycle began only on the following night, so the rest of the
budget went unused.

The real nightly logs show it about one night in three:

| Night | Left in the cycle | Run | Budget |
|---|---|---|---|
| 2026-09-23 | 12 | 12 repos in 18.5 min | 8 h |
| 2026-09-24 | 11 | 11 repos in 24.8 min | 8 h |
| 2026-10-05 | 2 | 2 repos in 11.4 min | 8 h |
| 2026-10-07 | 1 | 1 repo in 8.8 min | 8 h |
| 2026-10-10 | 19 | 19 repos in 24.1 min | 8 h |
| 2026-10-11 | 1 | 1 repo in 7.4 min | 8 h |

Most other nights end on the Claude usage limit, which is expected; these
ended with quota left. `round-robin` was not affected: its order already
wraps round the garden.

## The fix

- `overnight.continue_into_next_cycle`: a run's candidates are the cycle's
  leftovers, then every other repo in this run's strategy order. No repo is
  repeated within a run.
- `overnight.next_attempted(..., carried=...)`: once every leftover has had
  a real attempt and the run has moved past them, the cursor drops the
  finished cycle and keeps only the repos attempted since. If a leftover
  was skipped for a held lock, the cycle stays open and that repo is still
  owed.
- The start line now reads, for example, `183 repo(s) already attempted
  this cycle, 1 left before the next cycle begins`. The log marks the
  boundary with `continuing into the next cycle`. The dashboard's parser
  stops at `budget=`, so it is unaffected.

## Tests

- **Unit** (`tests/test_overnight.py`): `TestContinueIntoNextCycle`, 3
  tests, and 4 new `TestNextAttempted` cases:
  - the cycle boundary is crossed;
  - the leftovers are done but the next cycle has not started;
  - a leftover has no real attempt;
  - `carried` is ignored on a reset.
- **Integration** (`integration/test_offline_lifecycle.py`,
  `test_a_run_that_finishes_a_cycle_continues_into_the_next`): a two-repo
  garden whose cursor already holds one repo. The real CLI, run with
  `--strategy random` against the local GitHub stand-in, tends the
  leftover, then the other repo. It logs the boundary and leaves the cursor
  holding only the new cycle's repo. No write `gh` call is made.
- **Deliberate break:** with `continue_into_next_cycle` taken out of
  `cmd_overnight`, the integration test fails with `['it-fixture/second']
  != ['it-fixture/second', 'it-fixture/multiply']`. That is the nightly
  symptom: one repo, then stop.
- **Full suites:** unit and integration pass on Python 3.11 and 3.10.
  Integration has 61 tests, 15 of them live and skipped.

## Not yet seen for real

The 2026-10-12 nightly starts a fresh cycle (all 184 repos were attempted by
2026-10-11), so it does not reach a cycle boundary. The first real night to
cross one will be at the end of that cycle.
